Three sibling modules form the leaf of the HTTP API layer:
- `apiSources.pl` exposes the `sources/5` dispatcher (get/delete/post multipart upload, put multipart update, plus POST/PUT with `origin=` for copy/move) and json-rpc shims `sources_get/delete/copy/move/3`. It resolves paths through `kleio_resolve_source_file/3` using per-token `token_info`, delegates persistence to `persistence:kleio_file_*`, and returns either raw files via `http_reply_file` or JSON links built with `make_rest_url/3`.
- `apiIdentifications.pl` is a near-duplicate of `apiSources` specialised for `mhk_identification*.json` files; its own comment notes the duplication should be generalised later.
- `tokens.pl` owns the access-control substrate: it declares a `user_token(token,name,options)` fact persisted via SWI's `library(persistency)` (`attach_token_db/1`, `ensure_db/0`) and provides `generate_token/3`, `decode_token/3`, `invalidate_token/1`, `invalidate_user/1`, `is_api_allowed/2`, and helpers `get_stru_dir/2`, `get_data_dir/2`. Tokens carry an `api([...])` permission list and optional `life_span`; expiry is checked lazily in `expired_token/1`. A special `KLEIO_ADMIN_TOKEN` env var (or `$KLEIO_CONF_DIR/.kleio_admin_token` file) grants a fixed admin set of endpoints.

Dependency direction: both `apiSources` and `apiIdentifications` depend on `tokens` (for `is_api_allowed/2` and token option extraction), `restServer` (for URL building), `kleioFiles` (path resolution, MIME type), `logging`, and `persistence`; `tokens` depends only on `persistence`, `kleioFiles`, and `logging`. There is no cross-dependency between `apiSources` and `apiIdentifications`.

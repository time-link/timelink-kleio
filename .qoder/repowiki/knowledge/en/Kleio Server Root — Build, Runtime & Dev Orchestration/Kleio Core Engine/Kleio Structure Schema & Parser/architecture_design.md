Two-layer design:
- Data layer (`src/stru/*.yaml`): declarative schema definitions split by concern — `elements.yaml` for primitive/specializable element types, `groups.yaml` for group hierarchies with `source` inheritance, plus per-language variants under `pt-*`. `sources-structure.yaml` is the default entry point that `include:`s these fragments; `system.yaml` is the legacy-style root that includes `groups.yaml` and `elements.yaml`.
- Processing layer (`src/struSyntax.pl`, `src/struCode.pl`): `struSyntax` provides a DCG grammar (`cliocmd`, `parlist`, `val(...)`) driven by data predicates `params/2` and `command/2`; on each matched parameter it calls `execParam/3` in `struCode`, which accumulates command state as Prolog properties on atoms like `nomino`, `pars`, `terminus` stored thread-locally via `cmd/2`. On `close_command`, completeness is checked against `requiredParams/2` and the accumulated metadata is handed off to `dataDictionary:create_stru/1` for persistence.
- Legacy compatibility: `gacto2.str` (and its `.srpt`/`.json`/`.yaml` generated forms) is the canonical reference implementation of the same model in the original Kleio `.str` syntax, kept alongside the YAML sources so both formats are supported.
Dependency direction: `struSyntax` → `struCode` → `dataDictionary` / `persistence` / `errors`; the YAML files are pure data consumed by the loader outside this module's scope.

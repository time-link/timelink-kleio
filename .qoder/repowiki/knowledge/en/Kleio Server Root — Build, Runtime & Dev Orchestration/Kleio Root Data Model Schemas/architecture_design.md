Three complementary schema families coexist in this directory:
- `objects.yaml` / `objects.json`: entity taxonomy rooted at `object`, with `abstraction` as a mixin base (used by `topic`, `demand`, `acusacao`, etc.) and domain-specific branches (`acao`, `proparr` → `bemarr`/`fornarr`/`rendarr`, `bem` → `garantia`/`aforamento`/`arrendamento`/`escambo`, `obra`, `siza`/`sisa`, church bodies). The first entry is a bare `path: object` root declaration; subsequent entries are `group` blocks that declare a `name`, an optional `source` (inheritance), optional `part` (composition), and an `arbitrary` whitelist of allowed attribute/relationship slots.
- `actorm.yaml` / `pt-actorm.json` and `pt-actorf.json`: actor role schemas. `pt-actorm.json` builds a deep inheritance chain `person → male → actorm → n/presente/eleitor/…` plus hundreds of Portuguese legal/commercial roles (devedor, credor, fiador, tabeliao, beneficiario1..6, pagador1..5, tomador1..5, recebedor1..4-proc, etc.), each carrying the same `atr|ls|rel|referido|referida|pai|mae|filho|...` slot set. `pt-actorf.json` mirrors the same structure for female actors (`female → actorf → …`).
- `acts.yaml` / `acts.json`: event/act taxonomy rooted at `historical-act`, parameterised over `person|object|geoentity|abstraction|ls|atr|rel|end`; `event` extends it, `cevent` swaps `atr` for `attr`, and `pt-acto`/`ato`/`evento` provide Portuguese variants whose `part` list enumerates every actor-role slot name used across the model.

The `.yaml` files are the canonical human-readable source; the corresponding `.json` files are the machine-generated form consumed by the kleio-schema compiler (the JSON uses a flat array of `{group:{...}}` entries rather than nested objects). Dependency direction is strictly downward through `source:` — no cross-file references are needed because all slot names (`atr`, `rel`, `ls`, `referido`, `referida`, `pai`, `mae`, `filho`, `mulher`, `marido`, `pad`, `mad`, `procurador-pad`, `procuradora-mad`, `end`, `local`, `fonte_info`, `cheater`, `agente_financeiro`, `agente_seguros`, `transportador`, `cobrador*`, `recebedor*`, `pagador*`, `tomador*`, `beneficiario*`, `dador*`, `emissor*`, `representante`, `informador`, `defector`, `intermediario`, `fretador`, `receptor`, `destinatario*`, `vendedor`, `comprador`, `fornecedor`, `fiador`, `arrematante`, `quitante`, `quitado`, `abençoador`, `abençoado`, `perdoante-m`, `perdoado`, `vitima-m`, `testador`, `testamentario`, `testamenteiro`, `contraente`, `renunciante`, `procurador`, `escrivao`, `tabeliao`, `juiz`, `autoridade`, `padroeiro`, `apresentado`, `confirmante`, `comerciante`, `proprietario`, `requerente`, `requerido`, `pm`, `ts`, `testo`, `denunciante`, `acusado`, `enfermo`, `remetente`, `endossante`, `endossado`, `debitado`, `recebedor-proc`, `fornecedor`, `fiador`, `arrematante`, `quitante`, `quitado`, `abençoador`, `abençoado`, `perdoante-m`, `perdoado`, `vitima-m`) are treated as opaque strings validated only by presence in the declaring group's `arbitrary` list.
